# G3 Technical Specification Review

Date: 2026-08-27  
Artifact: `docs/hackathon-build/spec.md`  
Gate: G3 — architecture, WebMCP contract, privacy, threat model, and verification design  
Application code at review: none

## Review protocol

Three independent lanes reviewed the first complete specification:

1. WebMCP correctness, Devpost judge fit, compatibility, and demo proof (`scope_judge_review`);
2. product architecture, feasibility, dependencies, parser/recovery, and delivery capacity (`scope_product_review`);
3. security, privacy, PostgreSQL races, replay, retention, and black-box testability (`scope_repo_audit`).

All three returned **FAIL/CONDITIONAL**. G3 did not advance and application implementation remained prohibited. The primary agent then rewrote the affected contracts. The same three lanes must independently recheck the entire revised artifact; a pass requires all material findings closed and no new P0/P1 issue.

## Recheck verdicts

### Final decision on the oversized candidate

**FAIL — scope and architecture reopen; no application code may start from this candidate.**

The deep-remediation candidate reached 6,720 lines, 75,417 words, and 642,661 bytes. Its normative delivery surface included 23 HTTP/page surfaces, 15 relational tables, three blocking portability spikes, eight families of real-PostgreSQL concurrency proofs, multiple full browser/manual/external-client journeys, hosted retention/capacity evidence, and the final release proof. Application code remained at zero.

The product/feasibility and repository/security reviewers independently concluded that this cannot be implemented, integrated, remediated, accessibility-tested, externally verified, deployed, and recorded to the promised quality within the seven-day scope window while preserving the locked final 24-hour release reserve. A deliberately optimistic lower-bound count—one hour for each HTTP surface and table, two hours for each concurrency family and spike—already consumes 60 hours before the application UI/domain core, client integration, defects, accessibility, deployment, clean-room verification, video, or contingency. The P90 outcome is therefore necessarily beyond available build capacity.

Mechanical preflight on the decision candidate passed TypeScript-fence parsing and `git diff --check`, but mechanical validity cannot turn an infeasible contract into an approved build. The final contradiction pass was also still finding material Cartesian gaps and missing user-visible GET/failure contracts. Continuing to elaborate those protocols would deepen sunk-cost scope rather than improve delivery odds.

Disposition:

- preserve this file and the long `spec.md` as design/review evidence;
- do not call the candidate approved, frozen, production-ready, or implementation-ready;
- reopen G1/G2 and retain the winning loop: real six-tool WebMCP collaboration, two fixed synthetic packets, site-enforced source binding, one conflict/refusal, visible declaration, exact review, human-only atomic submission, and matching receipt;
- remove protocol breadth that judges do not need to see and that cannot be fully verified in the window;
- independently review the replacement scope, PRD, and practical spec before any application scaffold or code.

This is a quality decision, not a shortcut: the breadth is cut so every retained behavior can actually be implemented and proved.
